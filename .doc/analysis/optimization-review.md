# 阶段 02 · 性能与可优化空间审查

- 日期：2026-11-11
- 工程：`E:\Godot_v4.7.2-stable_mono_win64\Projects\demo`（Godot 4.7.2 Mono / C#）
- 结论：**有明确优化空间，而且第一瓶颈不在玩法算法，而在两盘的每帧重绘方式与后期射弹数量放大。** 按第 6 节顺序做 P0 项，可把 1× 帧时间从约 15.7ms 压到约 5–7ms，并把 600 秒后期 8× 从「7–14fps 尖峰」拉回 50–60fps 量级。

> 本报告所有数字都是本机实测（含临时探针/计数器，测量完成后已全部删除）。工程 39 个源文件 SHA256 与测量前一致，`--self-test` 70 项通过，`shots=5234 / territory=44928 / upgrades=10` 与 README 基线一致，可放心按结论施工。

## 2. 基线：耗时分布

### 2.1 无渲染（headless）模拟耗时

| 场景 | ms/tick | 相对实时 |
|---|---|---|
| 弹珠盘 8 球 | 0.063–0.067 | 125–132× |
| 战场空载（0 射弹） | 0.021 | ~400× |
| 联动开局 ~180s 前段 | 0.06–0.12 | 72–80× |
| 官方 self-test 口径：600 模拟秒 / 65.21s | 0.905（含后期高峰） | 9.2× |

**早期很宽裕，问题是「随对局时间恶化」**：

| 模拟时间 | 存活射弹 | ms/tick | 相对实时 |
|---|---|---|---|
| 60s | 41 | 0.107 | 78× |
| 120s | 74 | 0.306 | 27× |
| 180s | 556 | 0.656 | 12.7× |
| 240s | 689 | 1.653 | 5.0× |
| 300s | 215 | 1.668 | 5.0× |
| 360s | 172 | 0.625 | 13.3× |
| 420s | 456 | 0.568 | 14.7× |
| 480s | 552 | 0.490 | 17.0× |
| 540s | 566 | 1.436 | 5.8× |
| 600s | **1121** | **2.630** | **3.2×** |

**关键的射弹数量扩展实验**（固定其它条件）：

| 存活射弹 | ms/tick | 相对实时 |
|---|---|---|
| 256 | 0.34–0.35 | 23–24× |
| 1024 | 3.08–3.13 | 2.6–2.7× |
| 2048（容量上限） | 9.4–10.1 | **0.8–0.9×（低于实时）** |

数量 ×4 → 耗时 ×8.4，近似二次方增长。计数器归因（2048 发时，每 tick）：**6.37 次「全体推进」迭代、12,866 次 `PaintSegment`（本应约 2,048 次，6.3× 冗余）、38,802 次 `CircleTime`（盾/边界候选）**。原因见 P0-5。

### 2.2 窗口化渲染（1440×810，vsync 关，Debug，1×，早期）

用「隐藏某一层」隔离各层成本（同一会话、同一场景）：

| 配置 | 每帧 | Draw Call | 图元/帧 | 结论 |
|---|---|---|---|---|
| 完整 | **15.66ms** | 623 | 48.4k | ≈64fps，几乎吃满 60 帧预算 |
| 隐藏 PinballBoard | 6.67ms | 255 | 19.6k | **棋盘≈9.0ms/帧** |
| 隐藏 Battlefield | 11.11ms | 381 | 30.1k | **战场≈4.5ms/帧** |
| 两者都隐藏 | 1.39ms | 14 | 0.5k | HUD + 引擎 ≈1.4ms/帧 |

即 **1× 时约 14ms/帧花在「每帧重画变化不大的几何」上**，其中棋盘静态部分约 9ms。8× 实测（Debug）：`fpsAvg=36.4`、`frameMax=142ms`、draw call 峰值 2315、图元峰值 143k；`simRate` 仍显示 8.00×，实际是靠 70–142ms 的超长帧把积压的 tick 一次补完（长帧雪崩）。

### 2.3 构建配置 A/B（同代码、强制重编译、各 2 次取优）

> Debug 配置下 `Optimize=false`，JIT 不内联、不提升局部变量。命令行 `-p:Optimize=true` 实测：

| 项目 | Debug 默认 | Debug + Optimize | 提升 |
|---|---|---|---|
| 联动（60s 前段）ms/tick | 0.105–0.115 | 0.057–0.058 | **≈1.9×** |
| 2048 发 ms/tick | 9.4–10.1 | 6.6 | ≈1.5× |
| 128 球拥挤 ms/tick | 0.39–0.42 | 0.26–0.27 | ≈1.55× |
| `StaticSweep` | 5.3–5.5µs/次 | 3.8–3.9µs/次 | ≈1.4× |
| 单段涂色 | 199–226ns/次 | 126–152ns/次 | ≈1.5× |

**注意**：窗口化 1× 时优化构建几乎没有变化（55.0 vs 54.6fps）、8× 只提升约 9%（39.6 vs 36.4fps）——因为早期渲染侧占绝对大头；**该配置的收益会随对局后期模拟占比上升而变得显著**。

### 2.4 顺带确认「不是问题」的项

- **GC 不是瓶颈**：模拟层每 tick 只分配 0.1–14.5B；窗口化无渲染时约 0.3MB/s（主要是 UI 字符串），无 GC 停顿可测。
- 弹珠盘 128 球拥挤（极限）也只有 0.39ms/tick，`StaticSweep` 虽单次 5µs 但每 tick 仅约 6–40 次调用，不是首要项。
- 领土 RGBA 全量转换约 0.96–1.20ms/次；1× 下 10 次/秒可接受，**8× 下变成约 80 次/秒（≈8% 帧预算）**，需要按真实时间节流（P1-3）。

## 3. 优化清单（按收益/成本排序）

### P0-1【渲染·约 9ms/帧·低风险】PinballBoard 静态/动态分层

- **证据**：隐藏整个 PinballBoard 后帧时间 15.66→6.67ms（2.2 表）。
- **现状**：`src/Presentation/PinballBoard.cs:40-90` 的 `_Draw` 每帧重绘 4 层边框、101 条网格线、17 个钉（每个 3 个 48 段弧）、2 片多边形、22 段墙×2、6 个口袋环等；其中约 85–90% 与时间无关，真正变化的是口袋数值/闪色、16 个升力箭头、发射器、底部传送带能力栏。
- **改法**：新增 `BoardStatic`（Node2D + 小脚本）作为 `PinballBoard` 的子节点，把静态部分移入其 `_Draw` 并在 `_Ready` 只 `QueueRedraw()` 一次；动态部分留在 `PinballBoard._Draw`。**场景节点顺序必须是「BoardStatic → 动态层 → BallPool」**（父节点自身 `_Draw` 先于子节点绘制，顺序反了静态层会盖住球和动态内容）。
- **预期**：棋盘每帧成本 9.0ms → 约 0.2–0.5ms；1× 帧时间约 15.7→7ms；8× 早期帧时间约 27→18ms（36→约 50fps）。
- **风险/验证**：低。逐帧截图对比（`.doc/implementation/stage-02.png` 同角度），自检不受影响。

### P0-2【渲染·约 4.5ms/帧·低风险】Battlefield 绘制降本

- **证据**：隐藏 Battlefield 后 15.66→11.11ms（≈4.5ms/帧），且随射弹/粒子增多而上涨（8× 峰值 143k 图元）。
- **具体项**（`src/Presentation/Battlefield.cs`）：
  1. **涡流粒子 `:74-87`**：每粒 11 次 `DrawLine` + 1 圆，峰值 4 阵营×60 粒≈2.6k AA 段。改为同一折线点集 1 次 `DrawPolyline(points, color, 1, true)`（几何不变，1 调用/粒），预计 0.5–1.5ms/帧。
  2. **静态元素拆层**：进度轨道/25%-75% 刻度 `:98-107`、等级徽章外圈 `:108-109`、`领土/命中/待接入` 文本 `:111-113` 每帧 `DrawString` → 移入 `BattlefieldStatic` 子节点（同样注意顺序：静态层在前）。
  3. **护盾弧 `:88-94`**：96/64 段降为 48/32 段；射弹 4px 半透明光晕圆 `:64` 可去掉或只在低速时绘制。
- **预期**：战场 4.5ms → 1.5–2.5ms/帧；合计（P0-1+P0-2）1× 帧时间约 15.7→4–6ms，留出约 10ms 给 8× 的模拟。
- **风险/验证**：低到中（观感需截图对比；折线拐点可能差 1px）。

### P0-3【构建·模拟 1.5–1.9×·低风险】给 Debug 配置打开 JIT 优化

- **证据**：2.3 表；编辑器与命令行都加载 Debug 程序集，`Optimize=false` 是「官方 65s 基线」的一部分。
- **改法**：`Demo.csproj` 增加
  ```xml
  <PropertyGroup Condition="'$(Configuration)' == 'Debug'">
    <Optimize>true</Optimize>
  </PropertyGroup>
  ```
  改后 `dotnet build`（必要时 `-t:Rebuild`）重测同口径 self-test。
- **预期**：模拟 1.5–1.9×、渲染提交略降；后期（模拟占比高）收益更大。**不能单独解决 8×**，但它是所有后续改动的地基，1 行成本最低。
- **风险**：调试单步可读性下降（断点仍可用）。`ExportDebug`/`ExportRelease` 不受影响。

### P0-4【帧循环·防长帧雪崩·低风险】暂停/无 tick 跳过刷新 + 补步上限

- **证据**：8× 窗口化 `frameMax=142ms`、`fpsAvg=36.4`，造成「一帧慢→积压→下一帧补更多 tick→更慢」的雪崩；暂停时 `Main._Process` 仍每帧执行两盘 `Refresh`（≈14ms/帧的绘制与文本重建，视觉完全不变）。
- **改法**（`src/Presentation/Main.cs:51-60`）：
  - 暂停时或 `_accumulator < StepSeconds` 时直接返回（`TogglePause`/`Reset` 各补一次 `Refresh()`）；
  - `Math.Min(delta, 0.25)` 改为更小上限（如 0.05），并给 `while` 加每帧最多 16–32 步；超出时把 `_accumulator` 截断到 `StepSeconds`（丢弃欠账，宁可 8× 实际慢一点也不要长帧）。固定步长与确定性不变。
- **预期**：暂停帧 ≈0.03ms；8× 最差帧从 142ms 压到约 35–40ms，操作手感稳定。

### P0-5【模拟·后期 1.5–3ms/tick·高风险】射弹「最早碰撞」循环的二次方放大

- **证据**：2048 发时每 tick 6.37 次全局推进迭代、12,866 次 `PaintSegment`（应为约 2,048 次）、38,802 次 `CircleTime`；1024 发 2.09–3.13ms/tick，2048 发 6.6–10.1ms/tick。
- **原因**（`src/Simulation/BattleSimulation.cs:178-233` + `:244-258`）：每解决一次最早碰撞，就把**全部**存活射弹再推进一次并按小段重新涂色一次。总推进距离正确，但「涂色采样次数 = 存活数 × 碰撞数」，候选评估（`CircleTime`）也每轮全量重算。
- **改法（建议分两步，各自可独立提交）**：
  1. **事件缓存**：为每发弹缓存「下一事件（边界/盾）的绝对时间 + 目标」，每轮只取最小事件（同刻仍按发射 Id 稳定排序），仅对发生事件的弹和盾状态变化的弹重算；其余弹的事件时间在推进后只需线性减扣。可去掉约 90% 的 `CircleTime`。
  2. **涂色去重**：保留现有「全体推进」的顺序语义，但每 tick 每发弹只沿本 tick 的完整路径涂一次（把多个子段的采样合并），可把 12,866 次 `PaintSegment` 降回约 2,048 次。
- **预期**：2048 发场景 10.1→约 3.5–5ms/tick；600s 实际对局 2.63→约 1.2–1.6ms/tick（再叠加 P0-3 可到约 0.8–1.0ms/tick）。这是 8× 后期能跑起来的必要条件。
- **风险**：高。第 2 步会改变涂色的先后顺序→相同种子重放结果与现有 `shots/territory` 基线会变化；必须「先重跑并重新记录基线、再改 README 数字」，并确保每次 reset 后重放仍完全一致。建议单独一个提交，带 300s/600s 重放一致性检查。

### P1-1【渲染·8× 约 8% 帧预算】领土纹理上传按真实时间节流 + 调色板预计算

- **证据**：`src/Presentation/Battlefield.cs:41-52` 的上传门槛用的是**模拟时间**（0.1 模拟秒），8× 时变成约每 12.5ms 真实时间上传一次（≈80 次/秒）；全量 RGBA 转换约 0.96–1.20ms/次（Debug）。
- **改法**：门槛改为真实时间（`Time.GetTicksMsec()` 或累计 `delta`，例如每 100ms 真实时间一次）；像素转换改为预计算 `byte[5][4]` 调色板，循环只做索引写（2–3×）。
- **预期**：8× 下从约 8% 帧预算降到约 1%；1× 几乎无变化。风险低。

### P1-2【模拟·后期约 0.1–1ms/tick·低风险】固定数组 + 升序活跃索引表

- **证据**：战场每 tick 至少 3 次扫 2048 槽（`BattleSimulation.cs:156`、`:184`、`:248`）；`Spawn` 从 0 找空位，1121 存活时每 tick 约 206 次扫描；弹珠盘每趟仍做约 5.5k 次配对检查（128 容量 vs 实际约 12–30 飞行球）。
- **改法**：维护「升序活跃索引数组」+ `ulong[32]` 位图；遍历只走索引表，`Spawn` 取第一个 0 bit（与现有「槽位最小的空位」语义一致，保持稳定顺序）；某趟无重叠时提前 `break`。
- **预期**：成本与容量解耦，为阶段 03/04（大球、狙击碎片扩容量）留余量；后续持续收益。
- **风险**：中低。必须保持升序遍历（`Advance` 涂色顺序、`BattleTests` 依赖 `Projectiles[0]` 语义），改后重跑全部用例。

### P1-3【模拟/渲染·中小】一批低风险机械项

| 项 | 位置 | 改法 | 预期 |
|---|---|---|---|
| 静态墙预计算 | `src/Simulation/PinballGeometry.cs:65-102` | 预生成 `StaticWall{Start,End,Tangent,Normal,Length}`，不再每次 sweep 重算 tangent/normal/长度（含 2 次 sqrt） | `StaticSweep` −25%–40% |
| 盾半径缓存 | `BattleSimulation.cs:76-78,199-205` | 每 tick 缓存 4 个盾半径（盾值变化时更新），不在候选循环里反复 `Math.Log2` | 小，随目标数增长 |
| 涂色环形裁剪 | `src/Simulation/TerritoryGrid.cs:42-58` | 外层逐行算精确 dx 区间；`budget<cost` 时置 `blocked` 后 `break`（当前仍扫完 bbox） | 涂色段 −30%–50% |
| `Candidate` 展开 | `BattleSimulation.cs:187-193` | 局部队函数改为内联的比较（避免委托/闭包开销） | 爆发期 −2%–5% |
| `DrainRewards` 提前返回 | `PinballSimulation.cs:72-77` | 入口先判 4 个 `PendingRewards` 是否全 0 | <0.5%，3 行 |
| `UpdateSize` 里 `decay` 提升 | `PinballSimulation.cs:78-84` | 每个 tick 只算 1 次 `Math.Pow`（当前每球一次） | <0.5% |
| `BallView` 字符串缓存 | `src/Presentation/BallView.cs:11-20` | 值/可见性不变时不写 `Label.Text`；拖尾数组复用 | 削 GC/格式化 |
| 战场 Label 10Hz 节流 | `Battlefield.cs:31-40` | 8 个 Label 每帧重建文本改为 10Hz + 缓存 | 小 |
| `Main.Refresh` 分频 | `src/Presentation/Main.cs:61-68` | HUD 文本 10Hz；Events 用 `AbilityHits` 作缓存键 | 小 |
| 暂停时球/战场刷新 | 同 P0-4 | 无 tick 的帧不刷新 | 暂停时 ≈0 |

### P1-4【工程·建议】把性能基线变成可重复的回归检查

- 当前 self-test 每次约 80s，且只测正确性不测性能。建议加一个 `--bench`（headless）模式：固定种子跑 60s 前段 + 构造 1024 存活射弹场景，输出 ms/tick 与分配量；改动 P0-5/P1-2 后用它对比，避免「感觉变快了」。
- 阶段 03/04 前把「实体池统一形态」定下来（固定数组 + 升序活跃索引 + 容量上限语义），避免大球/狙击碎片再各自写一套全池扫描。

## 4. 8× 目标可行性推演

| 场景 | 当前 Debug | 只做 P0-1/2/4（渲染+帧循环） | +P0-3（构建优化） | +P0-5/P1-2（模拟重构） |
|---|---|---|---|---|
| 1× 帧时间（早期） | 15.7ms | 约 5–7ms | 约 5–7ms | 约 5–7ms |
| 8× 帧时间（早期） | 27ms / 36fps / 峰值 142ms | 约 18ms / 50fps / 峰值 <40ms | 约 17ms | 约 17ms |
| 8× 后期（600s，active≈1100） | 模拟 2.63ms/tick + 渲染 ⇒ 不可用 | 仍约 42ms/帧（模拟主导） | 约 25–30ms/帧 | **约 14–19ms/帧 ⇒ 50–60fps 量级** |

结论：**8× 后期 60fps 需要「P0-3 + P0-5 + P1-2」同时落地**；只做渲染优化只能让 1× 和 8× 早期舒服。若短期不做模拟重构，建议把 8× 定位为「快速演算」并给补步上限（观感 30–40fps、操作不掉帧），或暂时降到 4×。

## 5. 顺带发现的两个数据/玩法疑点（会影响 CPU 峰值）

1. **领土约 120 秒就被全部涂满**（44,928/44,928 格）。之后涂色只是在阵营间转移归属，但每 tick 仍在做同样的涂色采样计算。若这不是设计意图，建议核对 `PaintCostPerArea=0.0032`、初始半径与射弹密度——它是后期 CPU 与观感的共同来源。
2. **存活射弹数持续增长**（600s 时 1121 发），主要来自风暴波次与机枪连发；`ProjectileCapacity=2048` 远高于实际需要。可考虑：降低容量上限并依赖既有「池满时整波等待」规则、或给高预算射弹按时间/路径逐步衰减，把 CPU 峰值和「地图已涂满后仍大量存活」一起收敛。

## 6. 建议执行顺序与验收标准

1. **P0-3 构建优化**（1 行）→ 重跑 self-test + 同口径记录新基线。

## 7. 明确不建议做的「优化」

| 项目 | 原因 |
|---|---|
| 把 2048 射弹/128 球改 SoA 或 struct 数组 | GC 实测不是瓶颈；真正问题是全池扫描，用活跃索引表即可零分配解决，重构风险更大 |
| 事件驱动模拟（改变「全体推进」涂色顺序） | 会永久改变相同种子重放结果；除非像 P0-5 那样有意识地重定基线 |
| 改 `CellSize` / 网格分辨率 | 直接改领土面积、涂色成本与经验数值，全部玩法基线作废 |
| 多线程模拟 | 4 核还要跑渲染；同步/确定性/调试成本不划算 |
| csproj 里写 `ServerGarbageCollection` 等 GC 旋钮 | Godot 的 .NET 运行时配置由引擎 `GodotPlugins.runtimeconfig.json` 决定，项目 runtimeconfig 不生效；且 4 核上 Server GC 会多占线程 |
| 删 `config/features` 的 `Mobile`、把 Jolt 当性能项 | `Mobile` 是与 `rendering_method="mobile"` 配套的渲染器特征标签；Jolt 只是配置卫生，无帧时间收益 |
| 预改 shader / 开 MSAA 2D / pixel snap | 实测 GPU 填充不是瓶颈（隐藏两层后仅 1.4ms/帧），有视觉风险 |
| 把 128 个 BallView 或射弹改 MultiMesh/单节点批绘 | 节点变换更新比绘制命令便宜；MultiMesh 每帧 SetInstance 的 C# 调用可能更贵 |
| 改 `canvas_items`/窗口尺寸/像素对齐 | 当前组合已是最省 GPU 的配置 |
| 缓存半径/质量或把 `Math.Pow` 换 `Sqrt` | 半径含连续时间衰减，缓存=改物理；换 Sqrt 会改浮点轨迹，收益 <0.5% |
